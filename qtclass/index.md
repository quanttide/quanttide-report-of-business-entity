# 量潮课堂：教学与业务的一般方法

本文件收跨课程复用的判断，不收某门课的专属做法。课程具体想法见 [`courses/`](courses/index.md)，原始讨论报告见 [`courses/vibe-coding.md`](courses/vibe-coding.md)。

## 课堂教学的一般方法

- **参与度分四级**：没有参与、以玩家身份参与、以作者身份产出、以指导者身份帮助。分级跟课程内容无关，任何课都能照此给学员定位置。
- **反馈机制**：新手开发者一开始看不到自己的盲区，直到收到反馈才发现，所以具体的玩法体感反馈对他们特别有帮助——泛泛的表扬不如一次外部试玩。
- **项目选型判据**：入门项目要覆盖产品研发全流程（故事、美术、开发、测试、宣发）。能把一个复杂游戏做好，做什么 app 都差不多；计算器、日记本、打卡日历这类单项项目覆盖不到全流程。
- **练全局意识**：vibe 时代全局意识空前重要，不然一不小心就被 AI 带跑偏；投入到过分细节里而迷失，是所有人都会有的问题，教学要专门盯这一点。
- **嘉宾介绍分工**：本人和我们分别从不同角度介绍，且必须带上本人的 title、博士身份和研究领域——只让一方单方面介绍，容易把人介绍扁。

- **冷启动用参与度做门槛**：班级冷启动期清退没有参与的学员——一周内没有任何反馈即退出；参与的凭据是学习记录，一篇写清四件事：做了什么、遇到什么卡点、怎么解决、待完善的点在哪。跨课程通用。
- **把已做成果公开成池**：统一发布已做出来的成果，同时解两个问题——老学员缺试玩反馈、新学员不知怎么下手；公开池是拿到具体反馈的机制载体。

## 业务体系的一般方法（公司层，暂存于此）

这一节超出教学范围，是可迁移到其他业务线的方法论，先放在课堂业务线的 index 下，日后另立落点时迁出。

- **把可运营性当设计目标**：课堂业务的不确定性不靠天收的客户数量，而在我们自己的节奏。定目标看学员的活跃与交付，决策变量是管理策略——先看清自己能控制什么，再谈目标。
- **把靠天收改成可控结构**：来自餐饮调研的普遍痛点是无法预测客人数量、店主普遍说找不到规律；而课堂业务几乎每个组件环节主动性强、节奏控制准确。把靠天收的业务改造成这种结构，就能帮企业对自己的业务获得更强的控制感——这条可对外产品化。
- **把控制感做成游戏机制**：现有「打听消息」这类玩法本质是在增强控制感，但还比较初级，完全可以做得更真实；这样游戏的可玩性和对真实经营的启发都会更有效。这条是上一条方法论在产品上的第一次落地验证。
